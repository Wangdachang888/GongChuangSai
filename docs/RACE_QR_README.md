# 比赛动作状态机：启停区 → 二维码板

## 说明同步规则

每次新增、删除或调整比赛状态机动作时，必须同步更新本说明中的动作流程表、状态显示、可调参数、故障处理和实车验收步骤。代码与说明不一致时，以重新编译验证后的代码为准，并在本说明末尾记录变更。

本次实现二维码阶段的双启停区运动流程，并保留后续夹取状态机接口。二维码成功后完成当前扫描段并在公共汇合点进入下一阶段；二维码阶段完成不表示整场比赛完成。

## 运行模式与按键

正式比赛中 PE0 启动二维码路线，长按只在启动前切换启停区，运行中按下仍用于立即停止。夹取测试通过显式测试构建配置开启，不与正式入口混用。

二十圈加二十脉冲的实测累计偏差基本可控，说明原MOTORB脉冲换算没有明显问题。现在PC7改接为`SERVO_3`，原转盘电机的四段90°动作改由PC7舵机执行；不再向`STEPPER_AXIS_2`输出STEP脉冲，也不再使用MOTOEB。PC7由TIM8_CH2比较中断产生50 Hz舵机信号，PB14/PB15仍由TIM12控制。

`Config/app_mode.h` 的 `APP_RUN_MODE` 默认是 `APP_MODE_RACE`。原先 main.c 强制开启的舵机/步进测试分支改为统一选择：

| 值 | 模式 | PE0 用途 |
| --- | --- | --- |
| `APP_MODE_RACE` | 本次比赛扫码路线，当前默认 | 启动前短按启动、长按切换启停区；运行时按下停止 |
| `APP_MODE_SERVO` | 保留三舵机调试 | 原短按正转、长按反转 |
| `APP_MODE_STEPPER` | 保留步进调试 | 原短按上升、长按下降 |
| `APP_MODE_LEGACY` | 原底盘测试流程 | 原页面按键；会恢复 Square/Tune 启动逻辑 |

比赛模式不会运行原正方形、舵机按键、步进测试或 D36 文本命令。PE0 仍为上拉输入、按下接地。USART3 只归视觉模块使用。原 USART2 日志、ADC 电压采样和 DisplayNav 在此模式下不启动，以免阻塞或争用按键；旧模式保留这些功能。本次没有更改日志命名和 SD 卡写入逻辑。

操作顺序：

1. 上电后保持车体静止，完成原 IMU 初始化、预热和零偏校准。显示 `IMU WARMUP` 时不能启动；至少等待 18 秒，且必须得到 IMU 校准完成标志。
2. 屏幕 `Z1` 表示场地图右上角启停区 1，`Z2` 表示右下角启停区 2。默认 Z1，启动前长按 PE0 至少 700 ms 切换；松开不会启动。小车不会自动识别自己在哪个启停区。
3. 出现 `SHORT:START` 后，短按并松开 PE0 执行一次路线。上电时一直按住、随后松开不会触发运动。
4. 运行时再次按下 PE0，经 20 ms 消抖后停止；松开不会重启。比赛中的手动停止仅用于调试/终止本次运行。
5. 扫码成功后自动前往转 盘，最终显示 `MATERIAL READY` 和完整任务码；失败显示 `FAULT` 和错误编号。完成、停止或故障均锁定，复位后重新选择和启动。

依据用户提供的规则 PDF 第 11、15、19 页及右侧相机安装方式。当前配置把“车头朝原料区”解释为：**两区车头均朝场地图上方，即原料区所在边；右侧相机朝场地图右边界。** 此方向定义必须与实际摆车一致。若实际摆车朝图左方或斜向转盘中心，应修改对应 `RACE_ZONE*_HEADING_RAD`，不能直接按默认路线运行。

## 对接用户提供的 vision.c / vision.h

已读取附件，保留其协议中的 `R` 和 `#SEQ`，在 `race_vision.c` 与 `race_vision_protocol.c` 中实现当前扫码阶段所需部分。没有直接覆盖导入整份附件，也没有启动其 `#OBJ`、`#RING`、`#TRK` 或升降平台估算功能。

接线与实际工程一致：

- STM32 **PD8 / USART3_TX → OpenMV RX**。
- STM32 **PD9 / USART3_RX ← OpenMV TX**。
- 共地，115200、8 数据位、无校验、1 停止位；OpenMV 端 UART 和引脚按具体板型设置。
- 附件提到的 PB10/PB11 不适用于本工程：两脚已经用于 ICM20948 软件 I2C。
- PD5/PD6 属于原日志的 USART2，不能用作本次视觉接线。

到板前停稳后 STM32 发送**单字节 ASCII `R`，不附换行**。附件把它定义为复位、重新扫码；须确认实际 OpenMV 程序也实现此语义。成功上报示例：

```text
#SEQ,4,5,2,3,2,1,2,5,4,3,1,2\r\n
```

其中 `\r\n` 是实际回车换行，不是四个可见字符；单独 CR 或 LF 也接受。对应二维码原文 `452+321+254+312`。

解析要求：正好 12 个单数字，4 组依次为第一批颜色、第一批位置、第二批颜色、第二批粗加工位置；颜色 1～6、每批不重复、两批颜色集合相同；位置为 1/2/3 的排列。缺数字、多数字、超长、负数、零、重复位置、乱码和其他报文均不会完成扫码。

附件示例 `#SEQ,3,2,1,2,1,3,3,1,2` 只有 9 个数字，不足以表示本届的四组任务码。附件没有 OpenMV 发送端，因此**尚不能确认它实际上发的是 9 个还是 12 个数字**。若实际只发 6/9 个，必须修改 OpenMV 的序列上报，完整保留四组数据。发送端已有 QR payload 时，其格式转换可以是：

```python
payload = qr.payload()
groups = payload.split('+')
if len(groups) == 4 and all(len(group) == 3 and group.isdigit() for group in groups):
    uart.write(('#SEQ,' + ','.join(''.join(groups)) + '\r\n').encode())
```

将此段放入现有 OpenMV 识别成功分支，`uart` 是用户程序已有的 UART 对象。此示例仅说明编码，不是完整 OpenMV 驱动；STM32 仍执行完整内容校验。不要改成 `#SEQ,452,321,254,312`，那是 4 个整数而不是附件协议中的单标签序列。

本阶段不会发送 `K`，因为附件定义它表示抓取完成并推进任务；也不把 `#DONE` 当作扫码成功。开始扫码时清空已接收缓存，只接收扫码窗口内的完整报文；退出扫码后关闭接收结果使用。**原协议没有校验和、请求 ID 或复位确认，无法严格区分串口线上延迟到达的旧完整包。** 后续需要强会话隔离时必须双端扩展协议，当前未擅自更改线协议。

USART3 中断只收单字节进环形缓冲，解析在主循环，发送用中断方式。缓存溢出、硬件串口错误、接收启动失败均锁定 LINK 故障，避免丢字节后拼出看似有效的任务；需检查接线/波特率后复位。`USART3:RX READY` 仅表示本机接收已就绪，不表示 OpenMV 已握手。

## 动作组织与后续比赛阶段

夹取代码按“执行器动作层 + 非阻塞流程层”组织，结构参考控制代码包中的`Arm.c/Arm.h`与`Gimbal.c`：

| 文件 | 职责 |
| --- | --- |
| `App/app_pick_motion.h/.c` | 夹爪、夹持机构、PC7托盘和升降轴的动作接口；使用`OPEN/PRECLOSE/CLOSED`、`HOME/PLACE`、升降动作枚举，集中管理引脚对应关系和步数参数 |
| `App/app_pick_fsm.h/.c` | 非阻塞状态机；只负责动作顺序、完成判断、超时和故障切换，不直接拼接舵机角度或升降步数 |
| `Config/race_config.h` | 机械标定参数、速度参数、方向符号和流程开关 |
| `App/app_race.c` | 按键、比赛模式和状态机入口；每次轮询只调用一次夹取状态机 |

当前唯一动作入口是`PickFsm_Start()`和`PickFsm_StartReverse()`。旧MOTORB步进接口、PC7旧脉冲参数和转盘等待参数已从夹取配置中移除，PC7只通过`SERVO_3`动作接口控制。

`race_fsm` 是不依赖 HAL 的动作执行器，支持 MOVE、TURN、SETTLE、SCAN；`Race_RunActions` 可装入不超过 24 项的一段动作序列。MOVE/TURN 的 x/y/yaw 是相对**整段开始原点**的累计目标，不是相对上一动作的增量。SETTLE/SCAN 保持上一目标。`app_race` 负责按键、底盘命令、显示和视觉适配。

二维码成功解析后，`race_task_plan.c` 将 12 个字符转换为带批次、物料序号、颜色和位置参数的动作队列。队列顺序为：第一批取料 3 件 → 去粗加工区 → 放置 3 件 → 按顺序取回 3 件 → 去暂存区并放置 3 件 → 回原料区 → 第二批取料 3 件 → 去粗加工区 → 放置 3 件 → 按顺序取回 3 件 → 回暂存区码垛 3 件 → 返回启停区。第二批码垛位置通过颜色匹配第一批物料的位置得到，不直接误用第四组位置。当前只实现了第一件夹取动作；动作队列中的导航、粗加工放置、暂存放置和返回动作已生成参数，但未实现时会停留在对应队列项，不能宣称完成。

其他动作模块通过 `AppRace_TaskPlan()` 读取当前队列项：`kind` 是动作类型，`batch` 是批次，`item` 是批内序号，`color` 是颜色编号，`position` 是目标位置。动作模块完成后调用 `RaceTaskPlan_Advance()` 推进，不能在启动动作时直接推进。这样可以把导航、视觉对准、机械臂和夹取分别接入同一队列。

### 四细分下升降 42 电机理论用时

以下只计算升降 42 电机，不包含 PB14/PB15 舵机、夹紧/松开保持时间、状态机轮询延迟和超时保护。计算使用当前配置：800 脉冲/圈、5000 脉冲/s 最高频率、750 rpm/s 峰值加速度；普通动作使用本次重写的 jerk 限制 S 曲线，最终回零动作使用同样的 S 曲线加速，但进入制动区后直接采用梯形减速。

```text
脉冲峰值加速度 a = 750 rpm/s × 800 脉冲/圈 ÷ 60 = 10000 脉冲/s²
最高速度 vmax = 5000 脉冲/s
普通动作的 jerk = 50000 脉冲/s^3，加速度约 0.20 s 从 0 过渡到 10000 脉冲/s^2；减速收尾不低于 300 Hz后停止硬件队列；最终回零进入制动区后直接使用 -10000 脉冲/s^2，不会出现减速后再次加速
```

| 动作段 | 位移 | 脉冲数 | 理论峰值频率 | 加速时间 | 减速时间 | 升降电机时间 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 零位 → 80 mm | 80 mm | 5333 | 5000 Hz | S 曲线 | S 曲线 | 约 1.76 s |
| 80 → 24 mm | 56 mm | 3733 | 5000 Hz | S 曲线 | S 曲线 | 约 1.44 s |
| 24 → 170 mm | 146 mm | 9733 | 5000 Hz | S 曲线 | S 曲线 | 约 2.64 s |
| 170 → 零位 | 170 mm | 11333 | 5000 Hz | S 曲线 | 梯形 | 约 2.96 s |
| 零位 → 175 mm | 175 mm | 11667 | 5000 Hz | S 曲线 | S 曲线 | 约 3.02 s |
| 175 → 141 mm | 34 mm | 2267 | 5000 Hz | S 曲线 | S 曲线 | 约 1.15 s |
| 141 → 175 mm | 34 mm | 2267 | 5000 Hz | S 曲线 | S 曲线 | 约 1.15 s |
| 175 → 24 mm | 151 mm | 10067 | 5000 Hz | S 曲线 | S 曲线 | 约 2.70 s |
| 24 mm → 零位 | 24 mm | 1600 | 5000 Hz | S 曲线 | 梯形 | 约 1.02 s |

对应的升降电机纯运动时间为：

- 短按正向：`1.76 + 1.44 + 2.64 + 2.96 = 8.80 s` 左右，另含夹爪保持和舵机并行动作。
- 长按反向：`3.02 + 1.15 + 1.15 + 2.70 + 1.02 = 9.04 s` 左右；PB14 的 110°预夹紧与首次上升并行，不单独增加等待时间。

正向 PB15 在升到约 110 mm、剩余 60 mm（4000 脉冲）时启动；反向第一次在升到约 100 mm、剩余 75 mm（5000 脉冲）时启动，第二次在升到约 160 mm、剩余 15 mm（1000 脉冲）时回零。上述时间是连续时间模型，固件实际按 5 ms 轮廓周期和整数脉冲发送，实测会有少量量化误差。

当前没有接入上下限位输入或位置传感器。程序把上电时的机械位置视为零位，不会靠软件脉冲自动寻找零位；首次实车必须手动把升降机构放到零位，并确认反向流程的 175 mm 最高目标不撞机械上限。若要自动寻零，必须另接限位输入并增加受限速的寻零状态。

## 故障与验收

| ERROR | 含义 |
| --- | --- |
| 0 | 无故障；STOPPED 是按键终止 |
| 1 | 动作配置非法 |
| 2 | 移动、转向或停稳超时 |
| 3 | 8 秒内未获得有效完整任务码 |
| 4 | IMU 不可用、更新中断或状态含非有限值 |
| 5 | USART3 接收/发送启动失败、串口错误或缓存溢出 |
| 6 | 运行时主循环超过 250 ms 未完成一次轮询 |

运行中 IMU 断更触发停车；即使主循环卡住，TIM6 仍会检查轮询心跳并将四轮 PWM 清零。此保护依赖 CPU 与定时器中断继续运行，不代替独立硬件急停。

## 2026-11-17：数字圆环视觉闭环

本次视觉闭环在 `feature/ring-visual-closed-loop` 分支实现。STM32 视觉业务收口为 `Hardware/vision.c/.h`，OpenMV 运行文件只保留 `vision_openmv_stm32_v4_redownload/OpenMV/main.py`、`config.py` 和 `utils.py`。原有 `#SEQ` 任务码、`JOB,21`、`JOB,22`、`JOB,23`、二维码、六种颜色物料和旧物料任务接口继续保留。

圆环定位由比赛调度入口显式启动：

```c
AppRace_StartRingAlign(2U);
```

目标数字可填写 `1U`、`2U` 或 `3U`。该接口只允许在比赛状态为 `RACE_READY`、夹取机构空闲时启动；启动后圆环闭环独占底盘位置控制，完成或失败后释放控制权，不会和普通路线或夹取状态机同时写入底盘目标。默认 `RACE_RING_J00_PX_PER_M` 到 `RACE_RING_J11_PX_PER_M` 为零，表示尚未标定；此时可以接收视觉坐标，但不会驱动车辆。

闭环时序为：STM32 发送 `ALIGN,target,session` → OpenMV 回复 `ACK,ALIGN,target,session` → OpenMV 对当前新鲜图像发送 `POS,RING,target,dx,dy,cx,cy,session,step` → STM32 使用标定矩阵把像素误差转换为车体位移，并按当前航向转换到世界坐标 → 现有麦轮位置 PID 完成一次小步移动并确认速度稳定 → STM32 发送 `STEP_DONE,step,1`。如果本轮已在像素容差内，则发送 `STEP_DONE,step,0` 请求重新测量；连续四次新鲜观测满足容差后发送 `ARRIVED,RING,target,dx,dy,session,count`，OpenMV 回复 `ACK,ARRIVED,session` 和 `IDLE`。旧版扫码同时保留原始 `R` 触发字节，并发送新的封帧 `JOB,1`，因此旧 OpenMV 与 V4 OpenMV 均有兼容入口。

V4 封帧格式为 `@SEQ,LEN,BODY*XOR\n`。STM32 和 OpenMV 都校验长度、XOR、会话号和步号；重复帧、旧序号、旧会话、错误步号和过期坐标不会推进运动。STM32 中断只把字节放入缓存，协议解析、位置计算和串口发送均在主循环中完成；USART3 的接收、错误和发送完成回调仍各只有一个入口。

标定步骤：先把四个矩阵参数填入 `Config/race_config.h`，矩阵表示车体 `x/y` 位移对图像 `x/y` 像素变化的映射，单位为 px/m；用小幅、低速的单轴实测分别记录 `J00/J10` 和 `J01/J11`，确认正负方向后再启用非零矩阵。`RACE_RING_GAIN`、`RACE_RING_MAX_STEP_M`、`RACE_RING_MIN_STEP_M`、`RACE_RING_MAX_SPEED_MPS` 和 `RACE_RING_MAX_OMEGA_RADPS` 分别限制保守增益、单步位移、最小修正和运动速度。默认单步最大 50 mm，必须先用实测矩阵和低速空场测试。

圆环实车验收顺序：先只接收并检查数字 1/2/3 与 `POS`；再分别做车体 X、Y 小位移标定；确认矩阵有效后只启动一次低速 `AppRace_StartRingAlign()`；检查每个 `STEP_DONE` 都发生在编码器位置到位且速度稳定之后；最后连续验证四轮收敛、`ARRIVED`、`IDLE`、拔掉视觉串口后的超时停车和重复启动。电脑端 `tests/race/run.ps1` 已增加圆环 ACK、重复步号、标定位移、停稳、`ARRIVED/IDLE` 模拟测试；目标固件仍需使用 Keil/ARM 工具链实际编译和实车验收。
