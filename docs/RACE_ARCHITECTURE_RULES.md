# GongChuangSai 比赛任务函数式架构规范（Codex 必读）

> 规则定位：这是用户指定的**未来编程规范**。仅要求今后开发遵守；**不得以本文件为由立即全工程重构**。
>
> 参考来源：用户上传 `GongXun2025-main.zip`，其中 `控制代码/User/main.c`、`控制代码/CarBody/zpc_zxc.c`、`Chassis.c`、`Chassis_Path.c`、`Gimbal.c` 和 `Arm.c`。这是组织风格参考，不是可直接复制的源码模板。
>
> 适用范围：`refactor/architecture-v2` 及其后续比赛固件开发；与仓库现有 `AGENTS.md`、`docs/ARCHITECTURE.md`、`docs/DECISIONS.md`、比赛规则共同约束 Codex。

## 1. 最核心的要求

**上层比赛代码像 GongXun2025 的 main.c 一样，按有意义的任务函数顺序排列；中层函数组合阶段动作；底层模块各管自己的控制和执行细节。**

参考工程在 `User/main.c` 中以 `zpc_zxc_StartToPlate()`、`zpc_zxc_GetWuLiao(batch)`、`zpc_zxc_PlateToSeHuan1()`、`zpc_zxc_SeHuan1Process(batch)`、`zpc_zxc_SeHuan1ToSeHuan2(batch)`、`zpc_zxc_SeHuan2Process(batch)`、`zpc_zxc_GoHome()` 等函数表达主线。`zpc_zxc.c` 再调用 Chassis、Gimbal、Arm。

**阅读比赛总流程时，原则上不必深入步进、电机PID或UART代码，就能知道先做什么、后做什么。**

这是**任务函数式组织 + 现有非阻塞执行机制**，不是要求所有功能变成阻塞函数，也不是要求新建一个复杂的通用任务调度框架。

## 2. 唯一正式层级及调用方向

```text
Core/Src/main.c
│   程序入口、TIM6回调
│   不安排比赛业务
│
└── App/app_runtime.c
    │   运行模式、设备初始化、主循环调度
    │
    └── App/app_race.c
        │   唯一比赛总协调层
        │   组织任务顺序、发起和结束任务
        │
        ├── App/race_task_plan.c
        │   二维码任务数据、颜色、批次、工位
        │
        ├── App/race_fsm.c
        │   路线动作执行器
        │   MOVE / TURN / SETTLE / 扫码路段
        │
        ├── App/app_pick_fsm.c
        │   机械组合动作执行器
        │   抓取、释放、升降、旋转、转盘
        │
        └── 现有视觉对准应用逻辑
            JOB40 / JOB41 / 圆环对准
            微调、停稳、标定

Control/
    唯一底盘运动学、里程计、
    位置PID、速度PID

Hardware/ 与 OpenMV/
    IMU、步进、舵机、USART3、
    视觉解析和图像算法
```

### 禁止反向承担职责

- `AppRace` 不直接解析USART字节、不计算电机脉冲、不直接操作PWM/GPIO，不在比赛主线展开复杂的视觉数学或舵机等待。
- `RaceTaskPlan` 只管理业务任务数据和索引，不直接控制底盘，不成为第二个顶层比赛状态机。
- `RaceFsm` 负责一个动作序列的启动、到位、停稳、超时、故障，不决定下一批物料要去哪里。
- `PickFsm` 负责机械组合动作内部的序列及交错动作，不决定车辆导航路径。
- `Hardware/vision.c` 管理协议、会话、有效性、缓存、业务结果，不直接下发底盘移动。
- `Control/mecanum_chassis.c` 保持唯一底盘运动学和位置PID，不在业务层重复编写。
- 视觉对准应用层可以在 `AppRace` 授权控制权时使用现有位置环进行小步修正，但不能和普通路线同时写底盘目标。

## 3. 比赛总流程应当是什么样子

下面只是**代码组织风格示意**，并非声称已存在这些API，也不授权一次性实现完整比赛。

```c
/* 伪代码：按业务顺序排列 */

RaceTask_ScanQr();              // 两区扫码，在公共点汇合

RaceTask_GoMaterial();          // 去原料区

RaceTask_PrepareCamera();       // 相机升降、俯仰到工作位

RaceTask_AlignArea();           // JOB40 圆盘定位及微调

RaceTask_AlignPickupSlot();     // JOB41 固定抓取位对齐

RaceTask_GetMaterials(batch);   // 未来：按二维码取一批物料

RaceTask_RoughProcess(batch);   // 未来：粗加工

RaceTask_StoreMaterials(batch); // 未来：暂存或码垛

RaceTask_ReturnStart();         // 未来：返回原启停区
```

要求：

1. **一个业务函数代表有意义的比赛阶段，而不是一个电机动作或ACK。**
2. 顶层能直观看到整个流程，阶段内部再组合路线、摄像头、机械和视觉动作。
3. 各任务的参数使用 `RaceTaskPlan` 的颜色、批次、位置、顺序，不要在总流程重复展开每个物料的细节。
4. 路点、速度、容差、视觉标定放现有 `Config/` 或对应路线数据位置，避免到处散落魔法数。
5. 新功能先考虑在现有模块或接口中扩展，不要为了一个工位新建一个FSM文件。
6. 当前 `AppRace` 已有扫码及原料区逻辑，后续可按用户新需求逐步理顺；**文档同步这一批不应修改固件行为**。

## 4. 任务函数必须非阻塞

参考 GongXun2025 中有 `Delay_ms()`、`while(...)` 等等待模式，但**本工程不能照搬它们**。

- 现有 `AppRuntime_Poll()` / `AppRace_Poll()` 继续轮询任务，TIM6保持**每1ms电机更新、每10ms底盘环**。
- 一项任务必须有明确的“未开始 / 执行中 / 成功 / 失败或取消”语义；主循环每次处理当前步骤，不能卡住其他任务。
- 下发目标通常在动作进入时只执行一次，随后根据真实反馈、时间戳、停稳、超时等条件推进，不能在每次Poll中反复重置目标。
- 不得用 `HAL_Delay`、`Delay_ms` 或无界 `while` 等待视觉识别、底盘到位、升降、舵机完成；`main.c` 的无限主循环属于调度入口，不在此禁止范围。
- **允许少量顶层业务阶段**用于非阻塞任务切换；内部ACK、视觉重新采样、舵机忙等状态只放在负责该动作的子模块内。
- 不为抽象而强行加入 `TaskExecutorV2`、`RaceManagerV2`、每工位一套FSM、冗长回调或函数指针层。

## 5. 三个完成概念必须严格区分

| 层级       | 完成条件                                            | 禁止的误用               |
| -------- | ----------------------------------------------- | ------------------- |
| 单个动作完成   | 一段MOVE/TURN/SETTLE、视觉修正步、夹爪子动作完成                | 不能据此触发整个业务的下阶段      |
| 一个业务阶段完成 | 例如QR有效、到达(1400,290,0°)且停稳；或JOB40、JOB41均已确认且底盘稳定 | 不能仅凭QR有效就开始抓取       |
| 整场比赛完成   | 全部任务计划、两批物料、规定放置/码垛及返回起点完成                      | 不能把`RACE_DONE`当全赛完成 |

`RaceFsm` 中 `RACE_DONE` 当前主要表示**本次路线动作数组完成**，不是整场比赛完成。

下一个任务只能由 `AppRace` 在完整检查当前业务阶段结果后启动一次。

## 6. 底盘控制权与安全约束

- 当前任何时刻最多一个业务模块拥有底盘目标写权限，由 `AppRace` 授权、回收，`Control/mecanum_chassis.c` 始终是唯一位置环执行者。
- 全局人工停止、故障、IMU失效、视觉断连优先于当前任务，不得因视觉对准处理分支提前 `return` 而漏掉停止按键。
- 视觉结果必须属于当前任务及会话、数据新鲜有效，不得用旧QR、AREA、POS、ARRIVED推进新阶段。
- 实测坐标、航向、相机工作位、像素到位移矩阵、开环升降零位缺失时，不得伪造标定成功或擅自打开配置安全门。
- 所有动作具备明确超时、停止、恢复限速和状态归属；底盘与机构转向必须考虑场地边界及机构包络。
- 保留既有TIM6、USART2日志、USART3视觉、IMU、步进与舵机资源；未经允许不得改PID、轮径、轮距、驱动细分和硬件引脚。
- 比赛当前不做避障，不新增避障状态机或算法。

## 7. Codex必须遵守的具体工作方式

### 修改前

依次读取：

1. `AGENTS.md`
2. `docs/PROJECT_STATE.md`
3. `docs/ARCHITECTURE.md`
4. `docs/DECISIONS.md`
5. `docs/RACE_ARCHITECTURE_RULES.md`

检查工作区、当前分支、HEAD和真实源码。

列出目标业务顺序、现有可复用模块和预计修改文件。

新增源码或拆分模块，必须按AGENTS规则先征得用户批准。

### 修改时

- 优先采用最小补丁。
- 不新建功能相同的第二套状态机、PID、UART回调或 `legacy/v2` 双版本。
- 阶段完成后才允许启动下一阶段。
- 不把“现在还没做的完整比赛任务”一起擅自实现。
- 禁止取消标定安全门来假装跑通。

### 修改后

- 检查实际调用链和底盘控制互斥。
- 验证全局停止、超时、旧帧及完成条件。
- 运行关联主机测试、可用的Keil构建和 `git diff --check`。
- 更新长期文档。
- 按安全Git规则提交。
- 没有实测的项目写 `NOT_RUN`，不能用主机PASS代替实机PASS。

## 8. 可检查的代码简洁性标准

- [ ] 不打开底层驱动也能读懂比赛任务顺序。
- [ ] 顶层按有意义的业务函数编排，每个函数都有开始、执行、完成、失败语义。
- [ ] 一个工位不对应一套重复的顶层状态机或驱动。
- [ ] `RaceTaskPlan` 只提供任务数据，`RaceFsm` 只执行路线，`PickFsm` 只执行机械。
- [ ] 不把UART帧、位置PID、PWM/GPIO、升降脉冲计算塞进 `AppRace`。
- [ ] 每个动作是非阻塞的，有反馈、停稳、故障、超时、取消。
- [ ] 任何阶段转换都不会提前触发下一任务或使用陈旧数据。
- [ ] 同一时刻只有一个底盘目标写入所有者。
- [ ] 不出现old/new/v2并行编译实现或无必要的新抽象层。
- [ ] 测试、文档陈述与实际源码完成程度一致。

**一句话标准：比赛主流程像GongXun2025一样直观，实际执行继续使用当前工程已完成的非阻塞状态机和控制接口，而不是重造或阻塞底层。**
